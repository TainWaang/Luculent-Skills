## 一、事实状态与证据等级

### 四种信息状态

| 状态 | 定义 | 写法 |
|---|---|---|
| 已证实事实 F | 来源能直接支持，实体、时间和口径明确 | 直接陈述并就近引用 |
| 分析推断 I | 由多个事实推导，但来源未直接表述 | “据此判断/更可能”，说明推理链和反例 |
| 销售假设 H | 值得验证的机会或关键人判断 | 明确写“假设”，给验证问题 |
| 待核实 U | 公开信息缺失、冲突或已过期 | 说明缺口、责任对象和验证方法 |

禁止把I/H改写成F。报告中的匹配结论必须能追溯到F。

F/I/H/U只用于内部研究和证据台账。成品报告不设置“证据纪律”章节，也不向读者展示一套字母标签说明；在正文中自然使用“公开资料显示”“据此判断”“尚待客户确认”等表达。

### 证据置信度

- **高：** 一条直接S级来源，或两条相互独立且口径一致的S/A级来源；时间仍有效。
- **中：** 一条A/B级直接来源，或多条间接证据形成一致指向；仍存在关键未知。
- **低：** 仅有C级、搜索摘要、单一间接线索或来源明显过期。

置信度评价“信息是否可信”，匹配度评价“客户需求与朗坤智慧能力是否契合”。两者必须分别呈现。

### 证据台账字段

| 字段 | 内容 |
|---|---|
| 编号 | E001… |
| 目标实体 | 法定全称和集团层级 |
| 直接上级/最终集团 | 对下级单位分析时必填 |
| 主题 | 经营/组织/领导/政策/系统/项目/采购/竞争 |
| 事实或原文含义 | 忠实概括，不夸大 |
| 状态 | F/I/H/U |
| 事件日期 | 事实发生时间 |
| 发布/更新日期 | 来源时间 |
| 来源与链接 | 原始标题、发布主体、URL |
| 来源等级 | S/A/B/C |
| 置信度 | 高/中/低 |
| 冲突与限制 | 口径、过期、主体或访问限制 |
| 销售含义 | 对具体匹配方向的影响 |

## 二、项目状态与匹配度

### 公开状态

项目状态尽量使用公开事实，不使用虚假的成熟度分值：

| 状态 | 判定 |
|---|---|
| 已采购/已实施 | 已有中标、合同、建设、验收、扩容或运维证据 |
| 采购推进 | 已有采购意向、招标、比选、谈判或单一来源公示 |
| 已立项/筹备 | 已有可研、预算、科研立项、明确试点或责任单位 |
| 规划提及 | 正式规划、工作会或领导讲话明确提出建设方向 |
| 需求线索 | 存在客户特定问题或间接信号，但尚无正式项目证据 |
| 未见公开证据 | 只有行业通用压力，或没有找到客户特定信息 |

不得把“规划提及”写成“已经立项”，也不得把内部数科公司承接项目直接写成其已自主完成全部产品和实施。

### 匹配度

不进行百分制商机评分。根据事实给出定性判断：

#### 高匹配

同时具备多数条件：

- 客户或上级集团已有明确问题、任务、项目或采购信号；
- 朗坤智慧有直接对应的现行产品、交付能力和可核验案例；
- 集团统建边界与目标方向不冲突，或朗坤智慧能以明确专业边界补位；
- 目标单位、内部数字科技/三产公司和外部厂商之间的采购或合作路径基本清楚；
- 数据、接口、安全、实施和验收条件没有发现实质性冲突。

#### 中匹配

方向与朗坤智慧能力基本一致，但存在一项或多项关键未知：

- 只有集团政策或客户问题，尚无预算、项目或明确责任主体；
- 需要通过内部数字科技公司、设计院、运营商或总包方合作；
- 现有系统边界、数据条件、采购权限或在位厂商尚未核实；
- 朗坤智慧能覆盖部分专业域，但不是完整解决方案；
- 案例可参考，但与目标层级、行业或技术路线存在差异。

#### 低匹配

出现下列情形之一且暂无合理补位方式：

- 只有行业通用需求，没有客户特定证据；
- 集团已统一建设且明确禁止下属单位重复建设；
- 现有系统已覆盖核心需求，且没有改造、升级或专业补充空间；
- 目标主要属于朗坤智慧能力边界之外；
- 数据、工控安全、采购或交付条件存在明显冲突；
- 内部承接方和在位厂商形成封闭链条，未发现外部合作入口。

证据不足到无法判断时写“暂不判断”，不要为了表格完整强行给高/中/低。

### 匹配判断维度

每项匹配方向至少解释：

| 维度 | 需要说明 |
|---|---|
| 客户依据 | 目标单位真实问题、任务、项目或采购信号 |
| 上级传导 | 直接上级和最终集团的政策、统建和授权边界 |
| 现有基础 | 已有系统、数据、在位厂商和实施效果 |
| 内部承接链 | 数字科技/三产公司的角色、单一来源和外部分包可能 |
| 朗坤智慧适配 | 产品、案例、交付边界和差异化 |
| 限制条件 | 预算、关系、数据、集成、安全、验收和回款 |
| 建议 | 适合沟通的价值点、目标部门、合作方式和待核实问题 |

### 每个项目方向需要说明的内容

| 字段 | 内容 |
|---|---|
| 项目方向 | 使用客户业务语言，不堆产品名 |
| 目标实体/层级 | 集团、区域、场站、矿井或装置 |
| 问题与业务后果 | 当前方式、损失和责任 |
| 客户证据 | 事实编号和置信度 |
| 上级集团影响 | 支持、限制、统建、授权自建或未知 |
| 内部数科/三产公司 | 角色、承接方式、自研边界和合作可能 |
| 现有系统/在位厂商 | 已证实、候选或未知 |
| 朗坤智慧方案边界 | 做什么、不做什么、依赖什么 |
| 适合原因及不适用情形 | 为什么适配，什么情况下不适配 |
| 项目当前状态 | 已实施/采购推进/筹备/规划/线索/未见证据 |
| 价值指标 | 安全、可靠性、效率、成本、收益、合规 |
| 最小试点建议 | 范围、数据和价值验证方式 |
| 可能无法推进的因素 | 统建、数据、关系、采购、集成、交付 |
| 匹配度/置信度 | 高/中/低/暂不判断 + 证据高中低 |
| 待核实问题 | 需要向客户、上级集团或内部承接方确认 |

## 三、面向营销团队的报告结构

### 交付格式

允许用户选择：

| 选项 | 格式 | 适用场景 | 关键要求 |
|---|---|---|---|
| PDF版 | `.pdf` | 领导阅读、正式流转、归档 | 版式固定、逐页渲染校验 |
| 可编辑Word版 | `.docx` | 团队补充、删改、复用 | 正文、标题、列表和表格真实可编辑，不得图片化 |
| 双版本 | `.docx` + `.pdf` | 既要修改又要正式分发 | 以Word终稿为唯一内容源，再导出同版PDF |

用户未指定时默认PDF。用户提出“可编辑”“后续要修改”“给团队补充”时优先Word；明确要求“两种格式”“既要发领导又要修改”时交付双版本。格式选择不改变正文1万—3万字、证据和分析质量要求。

### 报告第一章：核心结论

控制在两至四页。根据研究目的选择以下内容，不为填满模板逐项罗列；完整客户研究通常覆盖多数项目，专题研究只保留与任务直接相关的项目：

- 客户当前最值得关注的情况；
- 上级集团数智化/AI规划对目标单位的具体要求；
- 当前最重要的三项业务或组织变化；
- 哪些部门和人员影响项目立项、技术、采购和验收；
- 内部数字科技/三产公司怎样承接项目，哪些环节可能外购或分包；
- 朗坤智慧最值得关注的项目方向及高/中/低匹配判断；
- 哪些因素可能导致项目无法推进，以及下一步最需要核实什么。

### 封面和目录

封面之后只保留报告目录，然后直接进入第一章“核心结论”。不得插入“使用说明、研究方法、证据纪律、红队审查、报告说明、信息边界”等独立页面或章节。研究截止日期放在封面或页脚；信息缺失和来源限制在相关正文或末尾来源清单中简要说明。

目录默认显示一级和二级标题。三级标题只用于内容复杂的部分，通常不进入目录。

### 完整报告的默认逻辑

面向朗坤智慧营销团队，默认按照以下顺序组织。用户有明确专题要求时可以合并、删除或扩展章节，但仍应保持“先看结论，再了解客户和相关人员，再看项目与厂商，最后判断朗坤能做什么”的逻辑。

1. **核心结论**
   - 1.1 客户当前最值得关注的情况
   - 1.2 与朗坤智慧最相关的需求和项目方向
   - 1.3 可能导致项目无法推进的因素及待确认事项
2. **客户业务、资产和经营情况**
   - 2.1 客户主体、产权关系和集团定位
   - 2.2 主营业务、重点资产和区域分布
   - 2.3 经营情况、发展重点和主要压力
   - 2.4 行业政策和区域环境对客户的实际影响
3. **上级集团、分子公司和重点单位**
   - 3.1 上级集团对数智化与AI建设的要求
   - 3.2 集团已统一建设的内容及下属单位可自主建设的范围
   - 3.3 分子公司构成、发展差异和重点生产单位
   - 3.4 建议优先关注的下属单位及原因
4. **组织架构、部门职责和领导情况**
   - 4.1 组织架构及数智化相关部门
   - 4.2 各部门在立项、技术、采购、使用和验收中的职责
   - 4.3 主要领导的分工、履历和近期调整
   - 4.4 与具体项目相关的负责人和需要进一步确认的人员
5. **数智化与AI规划、现有系统和建设空间**
   - 5.1 集团及目标公司的数智化与AI政策
   - 5.2 已建、在建和计划建设的主要系统
   - 5.3 数据、平台、AI、信创和工控安全基础
   - 5.4 现有系统未覆盖或仍需改进的业务问题
6. **内部数字科技公司、投资项目和招标采购**
   - 6.1 内部数字科技/三产公司的职责和已承接项目
   - 6.2 内部单一来源、外购产品和专业分包情况
   - 6.3 公开投资项目、技改项目和科研项目
   - 6.4 招标方式、采购规律和主要中标供应商
7. **现有供应商、竞争厂商和合作伙伴**
   - 7.1 已确认的现有系统建设和运维厂商
   - 7.2 主要竞争厂商及其客户基础
   - 7.3 设计院、运营商和其他合作伙伴的作用
   - 7.4 朗坤智慧相较现有厂商的优势和不足
8. **朗坤智慧可重点跟进的项目方向**
   - 8.1 高匹配项目方向
   - 8.2 中匹配项目方向
   - 8.3 低匹配或暂不建议重点投入的方向
9. **营销团队下一步需要关注的事项**
   - 9.1 建议优先联系的单位、部门和人员
   - 9.2 下一次客户交流应重点核实的问题
   - 9.3 需要客户或内部团队补充的资料
   - 9.4 需要持续关注的政策、人员和项目变化
10. **主要公开资料来源**

目标客户本身是集团时，将第三章调整为“集团战略及对下属单位的要求”；目标客户是二级或三级单位时，保留上级集团内容。专题报告可弱化与任务关系不大的章节，但不能把目录重新变成内部研究方法清单。

### 二级标题使用规则

- 每个一级章节通常设置二至五个二级标题，每个二级标题至少承载一个完整判断和相应事实。
- 连续三页以上只有一级标题和正文时，优先增加能够概括内容的二级标题。
- 一个二级标题下只有一两句话时，合并到相邻章节，不制造碎片化目录。
- 标题写清“什么对象、什么内容”，不要只写“分析、判断、审查、推进、洞察、启示”等泛化动作。
- 三级标题只用于区分不同业务板块、子公司、项目或产品方向；正文逻辑清楚时不强行增加。
- 同一主题原则上集中在一个章节中：上级集团要求放在第三章，项目和采购事实放在第六章，厂商关系放在第七章，朗坤智慧产品和项目建议放在第八章；其他章节需要引用时简要交叉说明，避免反复讲同一件事。
- 每个二级标题下按“先给本节结论—再列关键事实—最后说明对客户和朗坤智慧的影响或待核实事项”组织，但不要把这三句话机械写成三级标题。

### 成品标题用语

| 不得作为成品标题 | 应改成的直接表达 |
|---|---|
| 使用说明 | 删除，不设置该章节 |
| 证据纪律 | 删除，通过就近引用和来源清单体现 |
| 红队审查/对抗性审查 | 哪些因素可能导致项目无法推进 |
| 账户推进 | 建议优先联系的单位、部门和人员 |
| 购买中心 | 项目立项、技术、采购、使用和验收相关部门及人员 |
| 机会组合/机会卡 | 朗坤智慧可重点跟进的项目方向/项目方向分析表 |
| 客户画像 | 客户基本情况 |
| 战前分析 | 投标前客户、采购和竞争情况 |
| 竞争生态/竞合生态 | 现有供应商、竞争厂商和合作伙伴 |
| 上级约束/统建边界 | 上级集团的具体要求/集团已统一建设的内容及下属单位可自主建设的范围 |
| 信息边界/研究方法 | 不单设章节；在相关正文中说明资料缺口或判断依据 |

## 四、篇幅控制与动态分配

完整报告正文总量控制在10,000—30,000字。该范围是完整研究的篇幅和深度要求，不代表任何固定分析方法。

执行以下口径：

- 将第一章“核心结论”、章节分析和综合判断计入正文；不将封面、目录、页眉页脚、免责声明、来源清单、证据台账和附录计入正文。
- 根据用户最需要回答的问题、报告使用对象、客户层级、证据密度、决策影响和信息新颖度分配篇幅。
- 将最多篇幅用于能够改变销售判断的核心问题；压缩与任务关系弱、公开资料高度同质化或没有证据支撑的模块。
- 用户指定重点或提供目录时优先遵循；发现其结构会遗漏关键实体、上级集团要求或采购风险时，补充必要内容并说明原因。
- 纵向追踪、横向对标、案例比较、时间线和竞争矩阵均为可选方法。只有能回答当前问题时才使用，不为满足形式单独成章。
- 不将大段政策、招标文件、年报或官网原文复制到正文。只保留必要引文并用自己的分析解释其影响。
- 不通过拆分近义机会、重复公司简介、逐条复述招标公告或增加无判断表格达到字数。
- 对复杂集团将正文控制在18,000—30,000字；对信息充分的二三级单位控制在10,000—18,000字；根据证据密度调整，不按层级机械决定篇幅。
- 公开证据不足时，先补充上级集团、行业对标和同类单位比较；仍不足以支撑10,000字时，明确说明证据边界和所需内部材料，不编造或注水。
- 完整研究默认交付PDF，也可按用户选择交付可编辑Word或双版本。拜访快报、单一事实查询、某一专题核验不受本节最低字数约束。

## 五、标准表格

### 实体与上级链条

| 层级 | 主体 | 产权/管理关系 | 业务与核心资产 | 采购权限 | 数智化归口 | 证据 |
|---|---|---|---|---|---|---|

### 上级政策传导

| 上级政策/平台 | 发布层级 | 对目标公司的要求 | 强制/指导/试点/授权/未知 | 可自主空间 | 对朗坤智慧的影响 | 证据 |
|---|---|---|---|---|---|---|

### 内部数字科技/三产公司

| 主体 | 集团定位 | 内部承接方式 | 自研能力证据 | 外购/分包线索 | 控制环节 | 与朗坤智慧的可能关系 | 待核实项 |
|---|---|---|---|---|---|---|---|

### 领导与组织变化

| 时间 | 人员/部门 | 变化 | 专业线与职责 | 公开主题 | 影响判断（F/I/H） | 证据 |
|---|---|---|---|---|---|---|

### 数智化政策

| 时间 | 文件/讲话 | 适用层级 | 明确任务 | 责任主体 | 项目/资金信号 | 对朗坤智慧的含义 | 证据 |
|---|---|---|---|---|---|---|---|

## 六、写作要求

- 先给判断，再给事实链和推理；不要把搜索结果按网页顺序拼接。
- 段落围绕一个判断展开，表格承载精确映射和台账。
- 少用“赋能、抓手、打造闭环、全面提升”等空泛词；写明对象、动作和结果。
- 不写“该客户高度重视数字化”而不说明具体文件、投资或行动。
- 不写“朗坤智慧优势明显”而不比较现有系统、内部数科公司、竞品和交付边界。
- 不因信息负面而回避。经营困难、事故、项目终止、统建冲突和强在位厂商会直接影响判断。
- 效益测算只使用客户可核验基线、公式、假设和敏感性区间；不能把官网宣传值或其他客户结果直接套用。
- 来源链接就近放置；长报告末尾保留完整来源表和访问日期。
- 不输出机械的百分制商机评分、30/90/180天计划、里程碑或退出条件。
- 不让图表和表格代替分析。每张核心图表后至少给出一段“这意味着什么”，说明客户机制、采购影响或朗坤智慧判断。
- 第一章“核心结论”不得只是各章标题的缩写，应直接给出客户现状、变化原因、上级集团的具体要求、内部承接方式、优先项目方向和主要风险。
- 将大段比较清单转化为比较维度和差异结论；没有可比口径的数据不做伪精确排名。
- 使用适合领导阅读的正式中文，保持句子简洁、段落聚焦和观点密度；避免报告全文呈现同一种段落节奏。
- 不因用户提供的参考图、示例报告或模板中出现某种分析框架，就默认照搬其章节和比例；只继承用户明确要求的特点。
- 不把内部工作步骤、证据标签和质量检查名称写入成品目录。成品报告应像给营销管理人员看的客户研究，而不是研究人员的工作底稿。

## 七、交付前内部检查（不得写入报告）

### 实体测试

- 是否把同名公司、历史名称、集团与上市平台混在一起？
- 是否把深圳市朗坤科技股份有限公司或证券代码301305的信息误归到朗坤智慧？
- 子公司是全资、控股、参股还是托管？
- 经营和招标数据是否属于目标主体？

### 上级集团测试

- 目标为二级或三级单位时，是否研究了直接上级和最终集团？
- 集团政策对目标单位是强制、指导、试点、授权自建还是未知？
- 是否查清集团统建平台和禁止重复建设边界？

### 内部数科公司测试

- 是否识别集团内部数字科技/三产公司，而不是只分析外部竞品？
- 是否区分“内部单一来源承接”与“实际产品和实施由谁完成”？
- 是否用证据区分自研、集成、采购成熟产品、联合实施和专业分包？
- 是否分析朗坤智慧直签、联合、供货或专业分包的不同入口与限制？

### 时效与证据测试

- “现任领导”是否可能已调动？
- 项目是否已终止、重招、中标或投产？
- 系统案例是否仍在运行，还是多年前的一期项目？
- 是否多个转载实际来自同一原始稿？
- 是否把搜索摘要、宣传稿和推测当成直接证据？
- 历史价格样本是否可比，是否把预算、报价、中标价和合同额混用？

### 匹配度测试

- 高/中/低判断是否同时说明客户依据、集团约束、朗坤智慧适配和限制？
- 如果没有客户特定证据，是否降为低匹配或“暂不判断”？
- 现有系统为什么不能满足，还是实际上已经满足？
- 一线人员是否会增加重复录入、误报处置或运维负担？
- 数据、接口、工控安全和验收责任是否真实可行？
- 是否隐去了朗坤智慧不擅长或依赖伙伴的部分？
- 是否把同集团案例夸大为本单位关系？

只有通过这些检查，才可将某方向判断为高匹配。该部分仅供生成报告时内部使用，不得以“红队审查、对抗性审查、证据纪律”等名称出现在成品报告中。
